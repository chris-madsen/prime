# CPU + GPU оптимизации

## Цель

Использовать CPU и GPU как единый конвейер для вычисления масок, не дублируя одну и ту же работу и не создавая лишних промежуточных структур.

## Основная схема

- CPU строит seed, сегменты, стартовые offsets и checkpoint-состояние.
- GPU маркирует активные маски внутри непересекающихся сегментов.
- CPU сжимает, коммитит и пишет результат на диск.

## Согласование с архитектурой

Архитектура уже задаёт иерархию:

- `C4` — один канал.
- `B4` / тессеракт — два масочных слоя.
- `2T` / 24-cell — шесть масок.
- `2I` / 600-cell — тридцать масок.
- `E8` — шестьдесят масок.

Оптимизация должна уважать эту иерархию: CPU/GPU работают не по сырым числам, а по блокам `E8`, которые при необходимости делятся на 24-cell подблоки.

## Что делает CPU

### 1. Генерирует seed

CPU отвечает за:

- поиск базовых простых до `sqrt(N)`;
- вычисление wheel-210 состояния;
- определение стартовых offsets для каждого простого в сегменте;
- выбор формата хранения для блока.

### 2. Планирует сегменты

Лучше не делить диапазон случайно, а разбивать его на блоки, совместимые с архитектурой:

- внешний блок — `E8`;
- внутренний блок — `24-cell`;
- микроуровень — 60-битный selector.

### 3. Делает post-processing

CPU не должен быть узким местом в маркировке. Его задачи:

- сжатие активных блоков;
- checkpoint / resume;
- запись на диск;
- сбор статистики.

## Что делает GPU

### 1. Маркирует кандидатов

GPU должен выполнять только массовую однотипную работу:

- пометку кратных;
- обновление битсета сегмента;
- работу по residue-классам wheel-210.

### 2. Работает по крупным чанкам

Один GPU launch должен покрывать достаточно большой кусок, чтобы:

- amortize transfer cost;
- избежать частых `cudaMemcpy`;
- минимизировать синхронизации.

### 3. Пишет coalesced

Запись должна быть блочной:

- warp собирает локальные биты;
- потом один coalesced write в global memory.

## Оптимизации уровня данных

### 1. Wheel-210 в кандидатном пространстве

Не хранить и не просеивать заведомо мёртвые классы. Для каждого сегмента GPU и CPU видят только допустимые residue-классы.

### 2. `E8Bitmap` как базовый runtime-формат

Для средней плотности оптимален 32-байтный блок из четырёх `u64`:

```rust
#[repr(C, align(32))]
pub struct E8MaskBlock {
    selectors: [u64; 4],
}
```

Это даёт одну выровненную загрузку и хорошую SIMD-совместимость.

### 3. `SparseCSR` для редких блоков

Если плотность ниже примерно 11.7%, выгоднее `SparseCSR`, а не битсет.

### 4. `ImplicitFull` для полностью заполненных блоков

Если selector заполнен полностью, не хранить его вообще.

## Оптимизации CPU

### 1. Sparse-first decoding

На CPU горячий путь должен быть основан на:

- `trailing_zeros`;
- `word &= word - 1`;
- прямом применении callback к целевому битсету.

### 2. Dense-path отдельно

Если сегмент почти полный, лучше перейти на последовательный проход без ветвлений.

### 3. Без промежуточных Vec

Нельзя создавать временный список событий в горячем цикле. Нужна прямая запись в целевой битсет.

## Оптимизации GPU

### 1. Warp-level accumulation

Один warp должен собирать результаты в локальный mask-аккумулятор, а не писать каждый бит отдельно.

### 2. Shared-memory staging

Для каждого thread-block лучше использовать shared-memory staging buffer, а не слать каждую пометку в global memory.

### 3. Persistent CUDA pool

Контекст CUDA, streams и буферы должны жить постоянно. `cudaMalloc` и `cudaFree` не должны попадать в steady-state.

### 4. Split by density

Разреженные блоки обрабатывать sparse-ядром, а плотные — dense-ядром. Один kernel не обязан быть универсальным.

## CPU + GPU конвейер

### 1. Непересекающиеся сегменты

CPU и GPU не должны писать в один и тот же сегмент одновременно. Диапазон делится на непересекающиеся части.

### 2. Double buffering

Пока GPU считает текущий пакет, CPU готовит следующий и сжимает предыдущий.

### 3. Commit по сегментам

Единицей durability должен быть завершённый сегмент. Это позволяет возобновлять run без потери уже подтверждённой работы.

## Практический runtime

### CPU-only

Подходит для baseline, маленьких задач и отладки.

### GPU-only

Подходит для крупных однородных пакетов, если не нужен тяжёлый post-processing.

### Hybrid

Лучший вариант для production: CPU готовит и коммитит, GPU маркирует массивно и быстро.

## Что особенно важно

- Не гонять `mod` в горячем цикле, если можно хранить стартовые offsets.
- Не копировать лишние данные между CPU и GPU.
- Не дробить работу на слишком мелкие launch-единицы.
- Не смешивать геометрическую и runtime-иерархию: геометрия задаёт упаковку, а вычисление — битовую адресацию.

## Вывод

Оптимальная схема выглядит так:

- CPU: seed, offsets, scheduling, compression, checkpoint.
- GPU: массовое маркирование в сегментах.
- Хранилище: `E8Bitmap` + `SparseCSR` + `ImplicitFull`.
- Конвейер: double buffering и commit по сегментам.

Это согласуется с архитектурой `C4 -> 2T -> 2I -> E8` и не ломает её, а превращает в рабочую модель исполнения.
