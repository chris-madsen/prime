Да. Для **membership/query** оптимальная схема — это не список простых чисел, а **сегментированный битсет по колесу 2·3·5·7 = 210**, плюс блочная компрессия и редкие индексы для быстрого доступа.[^1][^2][^3]

## Оптимальная стратегия

Я бы делал так:

1. **Wheel 210**: хранить только числа, взаимно простые с 210, то есть 48 кандидатов из 210 возможных. Это сразу убирает большую часть заведомо составных чисел.[^2][^3]
2. **Сегменты фиксированного размера**: например, блоки по 2^20–2^24 кандидатов. Тогда для произвольного доступа нужно читать только нужный блок, а не весь массив.[^1]
3. **Bitset внутри блока**: один бит на кандидата.  
4. **RLE/word-aligned compression** для пустых или почти пустых блоков.  
5. **Индекс блоков**: хранить смещения сжатых блоков, чтобы можно было прыгать напрямую.

Это даёт хорошую комбинацию: быстрый lookup, хорошая локальность памяти, и возможность сжимать длинные нули/плотные области.[^5][^1]

## Оценка объёма

Для оценки возьмём верхнюю границу порядка \(2.66 \times 10^{12}\) для 100 млрд-го простого числа.[^6]
Тогда число кандидатов после wheel 210 сокращается примерно до доли \(\varphi(210)/210 = 48/210 \approx 0.2286\).[^3][^2]
Если бы хранить битсет **без дополнительного сжатия**, это было бы примерно:

- все числа до \(2.66 \times 10^{12}\): \(2.66 \times 10^{12}\) бит \(\approx 332.5\) ГБ;
- после wheel 210: \(332.5 \times 48/210 \approx 76\) ГБ.[^2][^6]

Но это ещё не итог, потому что простые — редкие единицы в битсете. Сегментированный битсет с хорошей компрессией обычно сжимает очень сильно, потому что большинство блоков содержит много одинаковых участков и длинные структуры повторения.[^4][^1]
Практически разумно ожидать **порядка 20–40 ГБ** для очень хорошо организованного compressed wheel-bitset, а иногда и меньше, если использовать большие блоки и эффективную кодировку пустых областей.[^5][^4]

## Что я бы выбрал

Если нужен **быстрый membership/query**, лучший компромисс такой:

- **Основной формат**: `wheel-210 segmented bitset`.
- **Компрессия блоков**: RLE + packed words.
- **Индекс**: массив смещений блоков.
- **Размер блока**: подбирать экспериментально, обычно от 64 КБ до нескольких МБ на блок с точки зрения распаковки.

Если нужен **только архив**, а не быстрые запросы, тогда выгоднее `delta-coded primes + block compression`.  
Если нужен **и архив, и быстрый query**, тогда `wheel bitset` обычно лучше.[^1][^5]

## Итого по памяти

Для 100 млрд простых:

- **плотный битсет без wheel**: ~332 ГБ;
- **wheel-210 битсет без сильного сжатия**: ~76 ГБ;
- **реально сжатый segmented wheel-bitset**: примерно **20–40 ГБ** как рабочая оценка;
- **дельта-кодированный список простых**: чаще больше для membership, но может быть компактнее как архив.[^6][^5][^1]

Если хочешь, я могу следующим сообщением дать **конкретный формат on-disk layout**:  
`header -> wheel pattern -> block index -> compressed blocks -> query algorithm`, уже без абстракции.

## Текущий статус реализации wheel-210 sidecar

Идея из этого файла уже частично реализована в `rust/e8_mask_codec` как дополнительный
архивный слой `wheel210/` поверх точного delta-coded архива простых.

Что уже есть:

- `wheel210/chunk_*.zst` — сжатые блоки вида `48-of-210 bitset + zstd`;
- `wheel210/manifest.txt`;
- `wheel210/index.tsv`;
- backfill-утилита `rebuild_wheel210_archive`, которая достраивает `wheel210/` из уже
  накопленного exact-архива без повторного пересчёта простых.

Первые реальные измерения:

1. На `10^6` простых:
   - exact chunk archive: около `977 KiB`;
   - `wheel210` sidecar: около `374 KiB`.

2. На большом архиве для первых уже готовых `83` chunk-ов:
   - exact archive: `581,009,671` байт;
   - `wheel210` sidecar: `274,052,011` байт;
   - отношение: примерно `0.472`.

Если экстраполировать это отношение на ранее полученную оценку exact-архива
около `93.322 GiB` для `10^11` простых, получается грубая текущая проекция:

- `wheel210` sidecar: примерно `44.0 GiB`.

То есть мы уже вышли значительно ниже exact-архива и почти вошли в целевую зону
`20–40 GiB`, обсуждавшуюся выше. Дальнейшее сжатие можно добивать за счёт:

- более агрессивного блочного layout;
- разрежённого кодирования внутри `210`-колеса;
- специальной компрессии длинных серий почти пустых wheel-блоков.

## Текущие runtime-метрики архива

Для long-run теперь доступны три отдельные дисковые метрики:

- `archive_exact_gib` — exact delta-coded архив простых;
- `archive_wheel210_gib` — compressed `wheel210` sidecar;
- `archive_total_gib` — суммарный размер обоих слоёв.

Они пишутся в progress-файл автоматически и видны через:

```bash
make count-status
```

Это удобнее, чем вручную смотреть `du`, потому что метрики синхронизированы с checkpoint/resume-сценарием.


### Wheel210-only режим хранения

Текущий production-режим архива должен использовать `--archive-mode wheel210`, чтобы не
держать на диске одновременно exact delta-coded архив и `wheel210` sidecar.

Именно `wheel210-only` соответствует целевой оценке порядка `20–40 GiB` на `10^11`
простых. Режим `both` сохраняется только как переходный/отладочный.
