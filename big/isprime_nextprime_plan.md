# Декларативный план имплементации `isPrime(N)` и `nextPrimeFrom(N)`

## Цель

Реализовать точные API `isPrime(N)` и `nextPrimeFrom(N)` для больших чисел порядка `10^1000` и `10^10000` в рамках существующей архитектуры масочного решета, не меняя математическое ядро и не вводя внешний вероятностный слой как обязательную часть алгоритма.

## Базовый принцип

Считать bitmask-подход не вспомогательным фильтром, а основной формой решета. Архитектура должна строиться вокруг локального масочного окна около заданного `N`, где число проверяется или находится следующий простой через точное вычёркивание в сегменте.

## Инварианты архитектуры

Сохранить уже принятую иерархию:

- `C4` — канальный цикл.
- `2T` / 24-cell — локальный исполняемый блок.
- `2I` / 600-cell — средний пакет.
- `E8` — крупный runtime-блок на 60 масок и 240 состояний.

Сохранить правило:

- хранить как `E8`;
- исполнять как 24-cell подблоки;
- не материализовать полные плотные маски, если можно работать через selector и affine update.

## Целевой API

Реализовать два публичных вызова:

```rust
pub fn is_prime_mask(n: BigUint) -> bool
pub fn next_prime_from(n: BigUint) -> BigUint
```

Дополнительно предусмотреть внутренние варианты:

```rust
fn classify_segment_mode(density: f32) -> SegmentMode
fn build_local_window(n: &BigUint, radius: usize) -> LocalWindow
fn mark_segment_cpu(window: &mut LocalWindow, ctx: &RuntimeCtx)
fn mark_segment_gpu(window: &mut DeviceWindow, ctx: &RuntimeCtx)
```

## Модель данных

### Вход

Для входного `N` хранить:

- само число `N` в `BigUint`;
- десятичный класс `r in {1,3,7,9}`;
- базовый индекс окна;
- размер локального сегмента;
- политику backend-а: `cpu`, `gpu`, `hybrid`.

### Runtime-блок

Базовым runtime-блоком оставить:

```rust
#[repr(C, align(32))]
pub struct E8MaskBlock {
    selectors: [u64; 4],
}
```

Поверх него оставить три режима хранения:

- `ImplicitFull`;
- `SparseCSR`;
- `E8Bitmap`.

## Режим `isPrime(N)`

### Шаг 1. Нормализация входа

Нужно:

- обработать `N < 2`;
- отдельно обработать малые простые;
- привести `N` к допустимому residue-классу;
- вычислить локальную фазу внутри сегмента.

### Шаг 2. Построение локального окна

Построить сегмент не от нуля, а вокруг `N`:

- определить `q0`;
- определить локальный диапазон блоков `E8`;
- вычислить отображение `BigUint -> (block_index, local_bit, channel)`.

### Шаг 3. Точное масочное вычёркивание

Для окна вокруг `N` выполнить локальное решето:

- активировать нужные `E8`-блоки;
- развернуть их как 24-cell подблоки;
- выполнить affine update по каналам;
- вычеркнуть составные позиции в целевом сегменте.

### Шаг 4. Чтение результата

После завершения вычёркивания:

- найти бит, соответствующий `N`;
- вернуть `true`, если он не вычеркнут;
- вернуть `false`, если он очищен маской.

## Режим `nextPrimeFrom(N)`

### Шаг 1. Нормализация старта

Если `N < 2`, вернуть `2`.

Если `N` чётное или не лежит в допустимом классе, перейти к ближайшему допустимому кандидату.

### Шаг 2. Построение первого окна

Построить локальный сегмент, начиная от `N`:

- стартовое `q0`;
- стартовый `E8`-блок;
- локальная позиция внутри 60-битного selector.

### Шаг 3. Локальное решето

Выполнить точное вычёркивание внутри сегмента и получить surviving candidates.

### Шаг 4. Поиск первого surviving candidate

- просканировать selector от стартовой позиции вверх;
- при нахождении первого невычеркнутого кандидата вернуть соответствующее число;
- если сегмент закончился, перейти к следующему сегменту и повторить.

## CPU-имплементация

### Обязательные свойства

- использовать `Sparse`-путь как основной;
- dense-путь включать только для очень плотных сегментов;
- не создавать промежуточные `Vec` событий;
- писать сразу в целевой битсет окна.

### Горячий цикл

Использовать:

- `trailing_zeros`;
- `word &= word - 1`;
- affine update вместо повторного полного пересчёта.

### План по потокам

- один поток координирует очередь сегментов;
- рабочие потоки обрабатывают разные блоки без пересечения;
- commit идёт только после полного завершения сегмента.

## GPU-имплементация

### Обязательные свойства

- использовать постоянный CUDA pool;
- держать device-буферы резидентными;
- не выгружать промежуточный список событий на host;
- писать сразу в device-bitset сегмента.

### CUDA-уровень

- один thread или warp работает по selector-слову или 24-cell подблоку;
- sparse-path является основным;
- LUT допустим как экспериментальный путь только для почти полных блоков;
- полностью заполненные блоки кодируются как `ImplicitFull`, а не через LUT.

### Передача работы

CPU и GPU должны получать непересекающиеся сегменты:

- `B = B_cpu ⊔ B_gpu`;
- pinned buffers переиспользуются;
- streams работают конвейерно.

## Hybrid-режим

### Декомпозиция

Использовать разделение по крупным сегментам:

- CPU берёт хвосты, малые окна и нерегулярные участки;
- GPU берёт крупные однородные пакеты;
- оба backend-а используют одинаковый логический формат `E8`.

### Конвейер

На steady-state одновременно происходят:

1. CPU готовит следующий сегмент.
2. GPU считает текущий сегмент.
3. CPU коммитит предыдущий сегмент.
4. runtime обновляет checkpoint и статистику.

## Индексация BigUint

### Что нужно реализовать

Для чисел порядка `10^1000` и `10^10000` нужно отдельно сделать слой индексирования:

- вычисление `q = floor((N - r)/10)` для `BigUint`;
- вычисление `block_index = q / 60`;
- вычисление `local_index = q % 60`;
- отображение `local_index -> (epsilon, i, j)` при необходимости.

### Требование

Эта часть должна быть чисто арифметической и не зависеть от materialized geometry.

## Проверка корректности

### Малые диапазоны

Сначала подтвердить точность на диапазонах, где возможна полная сверка:

- `10^6`;
- `10^9`;
- `10^12`.

### Сверка API

Нужно покрыть тестами:

- `is_prime_mask(2)`;
- `is_prime_mask(3)`;
- `is_prime_mask(composite)`;
- `next_prime_from(0)`;
- `next_prime_from(prime)`;
- `next_prime_from(composite)`.

### Большие числа

Для чисел с тысячами и десятками тысяч цифр сначала подтвердить:

- корректность индексации окна;
- корректность перехода между сегментами;
- корректность восстановления числа из позиции selector.

## Checkpoint и долгие запросы

Даже для `isPrime(N)` и `nextPrimeFrom(N)` сохранить тот же принцип durability:

- единица фиксации — завершённый сегмент;
- прогресс сохраняется атомарно;
- resume продолжает поиск с последнего committed window.

Это особенно важно для `nextPrimeFrom(N)` на очень больших входах, когда ответ может лежать не в первом локальном окне.

## Этапы внедрения

### Этап 1

Добавить `BigUint`-индексацию в существующий runtime и реализовать CPU-only `is_prime_mask`.

### Этап 2

Добавить CPU-only `next_prime_from` с переходом между сегментами.

### Этап 3

Подключить GPU backend для локального окна без изменения внешнего API.

### Этап 4

Подключить hybrid scheduler для больших локальных окон.

### Этап 5

Добавить benchmark-набор для:

- размеров `10^100`;
- `10^1000`;
- `10^10000`;
- разных радиусов локального окна;
- разных политик `cpu/gpu/hybrid`.

## Критерии готовности

Слой считается завершённым, когда выполнены условия:

- `isPrime(N)` и `nextPrimeFrom(N)` работают через ту же масочную архитектуру, что и prefix-runtime;
- нет отдельного альтернативного формата данных для больших чисел;
- CPU/GPU используют тот же `E8` runtime-формат;
- результаты воспроизводимы;
- long-run корректно продолжается после resume;
- производительность измеряется отдельно для CPU, GPU и hybrid.

## Итог

Имплементация должна расширять текущий runtime, а не строить параллельную ветку алгоритма. `isPrime(N)` и `nextPrimeFrom(N)` для очень больших чисел нужно делать как локальный exact-режим поверх того же самого масочного решета, той же `E8`-упаковки и той же CPU+GPU архитектуры.
